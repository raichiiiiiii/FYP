\section{Fabric Consortium Governance Requirements And Base Decision}

\textbf{Status:} Proposed for product-owner review\\
\textbf{Date:} 2026-06-06\\
\textbf{Scope:} Future Fabric channel governance feature for MEPN\\
\textbf{Decision owner:} Product owner with technical/security sign-off

\subsection{Executive Decision}

Because the product owner wants an in-app Fabric channel governance feature, MEPN should implement it as an \textbf{operator-assisted consortium governance workflow}, not as fully automated Fabric topology administration in the first release.

The recommended base decision is:

\begin{quote}
MEPN will manage Fabric channel proposals, invitations, approvals, readiness checks, audit evidence, and operator execution records. The app will not initially hold Fabric admin private keys or directly mutate Fabric channel topology. A platform/Fabric operator will execute channel config changes outside the app, then upload sanitized execution evidence back into MEPN.
\end{quote}

This is the easiest and safest version to manage and implement because it gives users a real product workflow while avoiding the hardest production risks: MSP private-key custody, channel config signing inside the app, peer/orderer lifecycle control, and partially automated consortium changes.

\subsection{Why This Model Is Best For The Current Project}

A fully automated \texttt{POST /api/v1/fabric/channels} that creates a real Fabric channel would require the application to custody Fabric admin identities, generate or sign channel config updates, coordinate signatures across organizations, and recover from partially applied topology changes. That is high-risk and too large for the current review/product-hardening stage.

The operator-assisted model is better because:

\begin{enumerate}
  \item It provides a visible Organization Admin feature.
  \item It keeps private Fabric admin material outside the application.
  \item It gives auditors a full approval/evidence trail.
  \item It is implementable with the current audit/outbox/evidence architecture.
  \item It can later evolve into automated execution if a managed secret store and operator agent are approved.
\end{enumerate}

\subsection{Base Architecture Boundary}

\subsubsection{In scope for the app}

The MEPN application may manage:

\begin{itemize}
  \item Fabric network metadata.
  \item Fabric channel metadata.
  \item Channel creation proposals.
  \item Channel invitation proposals.
  \item Organization acceptance records.
  \item Governance approvals.
  \item Readiness checks.
  \item Operator execution packages.
  \item Sanitized execution evidence.
  \item Audit events and hash-record evidence for governance actions.
\end{itemize}

\subsubsection{Out of scope for the first implementation}

The MEPN application must not initially:

\begin{itemize}
  \item Store Fabric admin private keys.
  \item Enroll MSP identities directly.
  \item Generate production MSP material.
  \item Sign channel config updates using admin certificates.
  \item Create or join peers automatically.
  \item Manage orderers.
  \item Submit channel config updates automatically.
  \item Change endorsement policies automatically.
  \item Act as a full Fabric CA/admin console.
\end{itemize}

\subsection{Proposed Domain Model}

Represents a logical Fabric network known to MEPN.

\begin{itemize}
  \item \texttt{id}
  \item \texttt{name}

\subsection{Proposed API Surface}

The API should make the governance boundary explicit.

\subsubsection{Network and channel registry}

\begin{verbatim}
GET  /api/v1/fabric/networks
POST /api/v1/fabric/networks
GET  /api/v1/fabric/channels
POST /api/v1/fabric/channels
GET  /api/v1/fabric/channels/:id
GET  /api/v1/fabric/channels/:id/readiness
\end{verbatim}

Important: \texttt{POST /api/v1/fabric/channels} creates a channel governance proposal and metadata record, not a real Fabric channel unless an approved operator execution step completes.

\subsubsection{Invitations and memberships}

\begin{verbatim}
POST /api/v1/fabric/channels/:id/invitations
GET  /api/v1/fabric/channels/:id/invitations
POST /api/v1/fabric/channel-invitations/:id/accept
POST /api/v1/fabric/channel-invitations/:id/revoke
GET  /api/v1/fabric/channels/:id/memberships
\end{verbatim}

\subsubsection{Proposals and approvals}

\begin{verbatim}
POST /api/v1/fabric/channels/:id/proposals
GET  /api/v1/fabric/channel-proposals/:id
POST /api/v1/fabric/channel-proposals/:id/approve
POST /api/v1/fabric/channel-proposals/:id/reject
POST /api/v1/fabric/channel-proposals/:id/cancel
\end{verbatim}

\subsubsection{Operator execution record}

\begin{verbatim}
POST /api/v1/fabric/channel-proposals/:id/operator-execution
POST /api/v1/fabric/channel-proposals/:id/operator-failure
GET  /api/v1/fabric/channel-proposals/:id/evidence
\end{verbatim}

The operator execution endpoint records what was executed and stores sanitized evidence. It must not upload private keys, admin certificates, or raw secret files.

\subsection{Roles And Permissions}

\begin{longtable}{p{0.25\textwidth}p{0.65\textwidth}}
\hline
\textbf{Role} & \textbf{Capability} \\
\hline
\texttt{ORG\_ADMIN} & Can request governance access but should not automatically mutate Fabric topology. \\
\hline
\texttt{FABRIC\_GOVERNANCE\_ADMIN} & Can create Fabric channel proposals and invite organizations on behalf of their app organization. \\
\hline
\texttt{PLATFORM\_OPERATOR} & Can mark proposals as operator-executed or failed and upload sanitized execution evidence. \\
\hline
\texttt{AUDITOR} & Read-only access to proposals, approvals, readiness, and execution evidence. \\
\hline
\texttt{PROCUREMENT\_OFFICER}, \texttt{FINANCIER\_USER}, \texttt{SHARIAH\_REVIEWER} & No Fabric channel mutation rights by default. \\
\hline
\end{longtable}

\subsection{Approval Thresholds}

\subsubsection{MVP thresholds}

\begin{longtable}{p{0.35\textwidth}p{0.55\textwidth}}
\hline
\textbf{Action} & \textbf{Required approvals} \\
\hline
Create new Fabric channel metadata/proposal & Requesting organization \texttt{FABRIC\_GOVERNANCE\_ADMIN} + \texttt{PLATFORM\_OPERATOR}. \\
\hline
Invite organization to channel & Existing channel sponsor \texttt{FABRIC\_GOVERNANCE\_ADMIN} + invited organization \texttt{ORG\_ADMIN} or \texttt{FABRIC\_GOVERNANCE\_ADMIN} + \texttt{PLATFORM\_OPERATOR}. \\
\hline
Accept invitation & Invited organization \texttt{ORG\_ADMIN} or \texttt{FABRIC\_GOVERNANCE\_ADMIN}. \\
\hline
Mark operator execution complete & \texttt{PLATFORM\_OPERATOR}. \\
\hline
Mark proposal failed & \texttt{PLATFORM\_OPERATOR} with failure reason. \\
\hline
\end{longtable}

\subsubsection{Future production thresholds}

For real production, policy updates and removal of members should require a majority or configured threshold of channel members. This should remain future work until consortium governance policy is approved.

\subsection{Status Lifecycle}

\subsubsection{Channel proposal lifecycle}

\begin{verbatim}
draft
  -> pending_approval
  -> approved
  -> operator_pending
  -> executed
\end{verbatim}

Failure and cancellation paths:

\begin{verbatim}
pending_approval -> rejected
pending_approval -> cancelled
approved -> cancelled
operator_pending -> failed
failed -> superseded_by_new_revision
\end{verbatim}

\subsubsection{Channel membership lifecycle}

\begin{verbatim}
invited
  -> accepted
  -> operator_pending
  -> joined
\end{verbatim}

Failure and removal paths:

\begin{verbatim}
invited -> expired
invited -> revoked
operator_pending -> failed
joined -> suspended
joined -> removed
\end{verbatim}

\subsection{Audit And Evidence Requirements}

Every governance mutation must emit an audit event.

Required audit event types:

\begin{itemize}
  \item \texttt{FABRIC\_NETWORK\_CREATED}
  \item \texttt{FABRIC\_CHANNEL\_PROPOSED}
  \item \texttt{FABRIC\_CHANNEL\_INVITATION\_CREATED}
  \item \texttt{FABRIC\_CHANNEL\_INVITATION\_ACCEPTED}
  \item \texttt{FABRIC\_CHANNEL\_PROPOSAL\_APPROVED}
  \item \texttt{FABRIC\_CHANNEL\_PROPOSAL\_REJECTED}
  \item \texttt{FABRIC\_CHANNEL\_OPERATOR\_EXECUTION\_RECORDED}
  \item \texttt{FABRIC\_CHANNEL\_OPERATOR\_EXECUTION\_FAILED}
  \item \texttt{FABRIC\_CHANNEL\_READINESS\_CHECKED}
  \item \texttt{FABRIC\_CHANNEL\_MEMBERSHIP\_JOINED}
  \item \texttt{FABRIC\_CHANNEL\_MEMBERSHIP\_FAILED}
\end{itemize}

Evidence records should store only sanitized metadata, command summaries, content hashes, and readiness results. They must not store private keys, PEM blocks, admin MSP folders, connection profiles containing secrets, or raw terminal logs with sensitive content.

\subsection{Readiness Checks}

\texttt{GET /api/v1/fabric/channels/:id/readiness} should return:

\begin{itemize}
  \item channel metadata status;
  \item required approvals status;
  \item invitation status;
  \item operator execution status;
  \item Gateway environment configured/not configured;
  \item chaincode configured/not configured;
  \item latest successful gateway probe if available;
  \item whether current application Fabric verification can use the channel.
\end{itemize}

\subsection{Security Guardrails}

\begin{enumerate}
  \item No Fabric admin private key may be stored in the app database.
  \item No PEM block may be rendered in UI or evidence docs.
  \item No Fabric admin MSP folder may be uploaded as evidence.
  \item Operator execution logs must be sanitized before storage.
  \item All governance actions require actor, organization, role, and audit context.
  \item Proposal retries must create new revisions.
  \item App Organization Admin and Fabric Platform Operator authority must remain separate.
  \item Production automation requires a new ADR before implementation.
\end{enumerate}

\subsection{Recommended First Build Slice}

The first implementation slice should be:

\begin{quote}
Read-only Fabric channel registry and operator-assisted proposal workflow metadata.
\end{quote}

Do not start with real channel creation. Start with records, approvals, readiness, and evidence. This creates product value quickly and keeps the security model manageable.

Suggested first sprint:

\begin{enumerate}
  \item Add Prisma models for \texttt{FabricNetwork}, \texttt{FabricChannel}, \texttt{FabricChannelMembership}, and \texttt{FabricChannelProposal}.
  \item Add read-only \texttt{GET /api/v1/fabric/channels} and \texttt{GET /api/v1/fabric/channels/:id/readiness}.
  \item Add \texttt{POST /api/v1/fabric/channels} as proposal creation only.
  \item Add audit events.
  \item Add admin UI page showing that operator execution is required.
  \item Add tests proving no direct Fabric topology mutation happens.
\end{enumerate}

\subsection{Final Base Decision}

MEPN should implement Fabric channel governance as a controlled, auditable, operator-assisted workflow first.

It should not initially implement direct channel creation, peer join, MSP enrollment, or channel config signing inside the app.

This gives the product owner the requested feature path while preserving the project's security, reviewability, and implementation feasibility.
