\section{Purpose and Scope}
The purpose of this SDD is to specify the software architecture and design baseline for \codename{}, a distributed e-procurement platform that allows SME organizations to automate procurement workflows and obtain project-based mudarabah capital from approved financial entities.

\subsection{Scope}
The design covers e-procurement workflows, restricted mudarabah finance workflows, scoped cross-organization collaboration, supply-chain graph/canvas visibility, ERP/accounting integration boundaries, e-signature and financial entity API integration boundaries, Hyperledger Fabric audit anchoring, API-side Fabric verification, operator-assisted Fabric consortium governance, report/evidence export, Docker Compose deployment, backup/restore, observability, UI/HCI evidence, and security architecture.

\subsection{Out of Scope}
Full banking-core replacement, autonomous Shariah/legal rulings, public blockchain settlement, production regulatory reporting, production penetration-test certification, real external provider certification, and direct Fabric channel topology administration by the MEPN application are outside this SDD baseline.

\section{Business Context / Problem Statement}
Traditional procurement creates friction through manual approvals, fragmented supplier records, disconnected ERP screens, invoice exceptions, maverick spending, contract leakage, poor spend visibility, and weak auditability. Mudarabah finance adds agency risk and profit-verification cost. \codename{} addresses both issues by making procurement workflow records the trusted evidence layer for restricted mudarabah: buyer contracts, supplier quotations, purchase orders, receipts, invoices, payments, project ledgers, reviewer decisions, Fabric anchors, and closure packs become the data basis for financier review and profit/loss verification.

\section{Current Implementation Baseline}
The Version 1.1 design baseline reflects the implemented FYP review package rather than only the original planning target. The repository currently contains:
\begin{itemize}
\item React/TypeScript web routes with protected app shell, role-aware navigation, dashboard/procurement/finance summaries, evidence, reports, operations, graph, organization profile, and reviewer-delighter surfaces.
\item NestJS/TypeScript API modules with Prisma persistence, reusable role checks, procurement and finance workflow guards, reports, loss exceptions, graph read models, Fabric verification, and Fabric governance endpoints.
\item Worker and outbox processing for retryable integration effects, Fabric anchoring, reconciliation, and worker heartbeat/status visibility.
\item Hyperledger Fabric Gateway support for hash-only anchoring and API-side chaincode verification; mock Fabric paths remain available for deterministic tests but are never reported as real proof.
\item Operator-assisted Fabric consortium governance for network/channel metadata, proposals, invitations, approvals, readiness checks, operator execution records, and sanitized evidence.
\item Docker Compose and Azure Student VM deployment evidence with mounted Fabric Gateway secret material under \texttt{/run/secrets/fabric}.
\item Automated evidence: final validation matrix, deployment evidence, VM-local Fabric proof screenshots, report export evidence, graph no-leak evidence, backup/restore proof, accessibility automation, and UI/HCI route-health evidence.
\end{itemize}

Remaining production-hardening work includes real OIDC provider UAT, PDF/spreadsheet reports, object-storage backup automation, manual screen-reader/mobile review and participant SUS study, external ERP/e-signature/payment provider adapters, and any future direct Fabric topology automation.

\section{High-Level Architecture}
\codename{} uses a distributed, self-hostable modular monolith with explicit bounded contexts, adapter-based integrations, an append-only audit subsystem, a transactional outbox, and optional Hyperledger Fabric anchoring. For MVP, this avoids microservice operational complexity while preserving service boundaries for later extraction.

\subsection{Core Principles}
\begin{enumerate}
\item SME-owned node is the operational system of record for the organization's data.
\item Procurement evidence drives mudarabah due diligence, monitoring, profit/loss calculation, and closure.
\item Full confidential payloads stay off-chain; Fabric anchors hashes and minimal metadata.
\item External systems are unreliable by default; use adapters, retries, idempotency, and reconciliation.
\item Authorization is enforced at gateway, service, and data-access layers.
\item Material business actions create audit events with correlation IDs.
\end{enumerate}

\subsection{Major Data Flow}
Buyer contract or sales order creates a procurement opportunity. The opportunity generates an evidence checklist and mudarabah capital application. Financier and Shariah reviewers approve or reject. Approved applications generate a restricted contract and e-signature package. Controlled disbursement funds procurement execution. Purchase orders, receipts, invoices, payments, ERP postings, and buyer revenue update the project ledger. Profit/loss is calculated from linked evidence. Closure pack export includes contract, approvals, ledger, distribution/loss decision, audit events, and Fabric anchors.

\section{Security Architecture}
Production users authenticate through OAuth/OIDC; the guarded development/UAT login path is a review convenience and must be disabled for production-like deployments unless explicitly enabled. Authorization combines organization membership, role, workspace scope, object ownership, object state, and policy conditions. TLS protects all browser, API, ERP, finance API, e-signature, and Fabric gateway traffic. Secrets are held in a secrets store or deployment-approved equivalent and may be mounted into containers as read-only files for the current VM deployment. Secret values, PEM blocks, private keys, tokens, and generated secret env files must not be logged, committed, or included in evidence. Confidential payloads are stored off-chain; Fabric receives hashes and minimum metadata only. Fabric governance records channel administration state, but channel-admin private keys and direct channel topology mutation remain outside the application boundary.

\section{Scalability and Performance Design}
Interactive pages use pagination, server-side filtering, cached reference data, and asynchronous export jobs. Workflow transitions commit local state and audit/outbox events quickly while deferring ERP/Fabric/e-sign/finance API effects to workers. PostgreSQL indexes organization, workspace, status, project, supplier, document number, lifecycle date, and audit correlation IDs. Search indexes and materialized views can support audit search and analytics. Graph/canvas loads filtered visible subgraphs rather than the full network.

\section{Reliability, Availability, Backup, and Disaster Recovery}
The system continues core local procurement when Fabric is unavailable and shows pending-anchor, unavailable, failed, or mismatched verification states truthfully. ERP, finance API, e-signature, Fabric, report export, and webhook integrations use retry and idempotency where they create external side effects. Backup proof currently covers PostgreSQL logical backup, restore, and restore smoke checks; object-storage backup automation, scheduled retention, and off-VM storage remain hardening. SME self-hosted deployments target RPO 24 hours and RTO 8 hours, matching the SRS.

\section{Deployment Architecture}
Docker Compose is the MVP deployment baseline. Deployment units are reverse proxy, frontend container, backend API container, worker container, PostgreSQL, object storage-ready volume or service, Redis/queue where configured, optional search index, and backup job. The Azure Student VM review deployment materializes Fabric Gateway identity, private key, TLS CA, connection profile, and generated env metadata under \texttt{/run/secrets/fabric}, mounted read-only into API/worker containers. Helm/Kubernetes is a future managed-deployment option for financial entities or consortium operators.

\section{Observability: Logs, Metrics, Tracing, Alerts}
Logs are structured and include timestamp, service, module, correlation ID, actor, organization/workspace when allowed, event type, and error code. Metrics include request latency, workflow transition duration, queue depth, retry count, database pool state, object store errors, adapter failures, pending anchor age, backup status, worker heartbeat freshness, report export lifecycle, and authorization denials. Traces follow requests through API, domain services, database, outbox, workers, and external adapters. The operations timeline provides reviewer-safe summaries of worker, outbox, reconciliation, Fabric, report, backup, and deployment events without raw payloads or secrets. Alerts cover high 5xx rate, queue backlog, Fabric anchors stuck, ERP sync failures, object storage failures, stale workers, and failed backups.

\section{Glossary}
\begin{description}[leftmargin=40mm,style=nextline]
\item[ADR] Architecture Decision Record.
\item[C4] Context, Container, Component, and Code diagram hierarchy for software architecture.
\item[Fabric anchor] Hyperledger Fabric transaction containing event/document hash and minimal metadata.
\item[Mudarabah] Islamic partnership where the capital provider supplies capital and the entrepreneur/operator manages the venture, with profit shared by ratio and genuine loss borne by capital unless breach/negligence/fraud applies.
\item[Outbox] Durable integration event store used for retryable external side effects.
\item[Workspace scope] Authorization boundary for a selected opportunity, project, or cross-organization collaboration area.
\end{description}
